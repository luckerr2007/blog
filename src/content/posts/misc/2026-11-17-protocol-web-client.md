> 这是一次针对测试样本的协议研究复盘。文中隐去目标名称、包名、接口地址、密钥、设备标识和可复现步骤，不构成对任何服务的访问授权。影视内容版权归原权利人，请勿用于未授权访问或分发。

把一个 App 的请求当成“一条 URL 加一个 JSON”，是理解移动端协议时最常见的错误。

真正发出去的一个请求，可能同时包含：设备身份、公共参数、请求签名、加密信封。任何一层对不上，服务端都可能只回一个很模糊的错误。排查时最耗时的不是写代码，而是判断“现在到底是哪一层错了”。

一句话版本：**先证明你是谁，再填一张快递单，再盖防伪章，最后把内容装进密封袋。**

本文只谈协议层，不展开页面、播放器和前端实现。

```text
设备身份  →  公共参数  →  请求签名  →  加密信封  →  服务端
 门禁卡       快递单        防伪章        密封袋
```

| 层 | 类比 | 解决的问题 | 典型失败 |
| --- | --- | --- | --- |
| 设备身份 | 门禁卡 | 区分官方客户端、版本和设备 | 设备码不匹配、换版本失效 |
| 公共参数 | 快递单 | 风控、路由、排障 | 字段缺失、类型错、编码错 |
| 请求签名 | 防伪章 | 防篡改、防重放 | 缺签名、验签失败 |
| 加密信封 | 密封袋 | 防窃听、防修改 | 解密失败、长度错、类型误判 |

## 一、第一层：设备身份，不是随机 UUID

很多接口会用 UUID 或随机字符串标识设备，但这类值很容易伪造。更严格的做法，是把“设备是什么”变成一串可计算的指纹：签名证书摘要、包名、版本号等稳定信息参与派生，最后得到一个固定长度的设备码。

可以把它理解成门禁卡：卡号不是随便发的，而是由身份证、单位、有效期一起算出来的。服务端保存一份白名单，只有算出来一致的设备才放行。

这一层解决的问题是：

- 区分官方客户端和通用脚本；
- 把请求绑定到某个包名、版本和设备；
- 让“换一个客户端随便调接口”变得更麻烦。

但它不是身份认证。设备指纹可以被复制，也可以被重放；它只能提高门槛，不能证明“现在操作的是真人”。对用户来说，这一层还带来一个副作用：换设备、换版本、清数据，都可能被当成新设备。

## 二、第二层：公共参数，一张很长的快递单

第二层是每个请求都会带上的公共参数：平台、系统版本、机型、网络、分辨率、应用版本、时间戳、随机串等。它们通常放在自定义请求头里，而不是业务参数里。

为什么需要这么多字段？因为它们同时承担三件事：

1. **风控**：判断请求像不像正常客户端；
2. **路由**：决定走哪条线路、哪个版本、哪个灰度策略；
3. **排障**：出问题时能定位到设备、版本和网络环境。

这一层最容易被低估的，是“类型”也是协议的一部分。数字写成字符串、字段名大小写不一致、少一个包名、参数被 URL 编码两次，都可能让服务端在进入业务逻辑之前就直接拒绝。对开发者来说，这就像快递单上把电话写成了文字：内容看起来没错，但仓库的机器读不了。

所以协议研究不能只记录“有哪些字段”，还要记录：

- 字段的顺序；
- 字段的类型（数字还是字符串）；
- 是否参与编码；
- 缺省值是什么；
- 哪些字段是服务端强制的。

## 三、第三层：签名，防伪章不是密码

第三层是签名。常见做法是：客户端用私钥对“时间戳 + 随机串 + 版本号”等内容签名，服务端用公钥验签；有些实现还会再加一段由对称密钥派生的短校验值。

它的目的不是“保密”，而是：

- 证明请求确实由持有私钥的客户端发出；
- 防止请求在传输过程中被篡改；
- 配合时间戳和随机串，增加重放成本。

可以把它理解成文件上的防伪章：盖章不能隐藏文件内容，但能证明文件没有被换掉。

这里有一个很关键的安全分界：**签名必须由服务端真正验证，不能只检查“有没有签名”**。如果服务端只判断字段存在，或者只在某个配置缺失时才报错，那签名就退化成了一种形式主义。攻击者不需要私钥，只需要知道“要带这个字段”，就能绕过检查。

另一个常见问题是：客户端持有私钥，私钥就一定会被提取。非对称签名只解决了“服务端不需要保存客户端私钥”，并没有解决“客户端不可信”。所以签名方案必须配合短期凭证、设备证明、重放缓存和服务端风控，单靠一个静态私钥是不够的。

## 四、第四层：加密信封，密封袋与回执

第四层是业务数据本身。样本没有用 JSON，而是把参数拼成 `k=v&k=v` 的查询串，拼上时间戳后做分组加密，再把密文拆进 protobuf 的多个字段。响应也不是普通 JSON，而是一个 `code / msg / data` 的信封，`data` 有时是明文 JSON，有时还要再解一层。

protobuf 可以理解成一张双方约定好的二进制表格：字段编号、类型、长度按固定规则排列，不像 JSON 那样把字段名写出来。它的优点是紧凑、解析快，缺点是“看不懂”——少一个字节，后面全错位。

这一层的设计目标通常是：

- 不让业务参数在网络上裸奔；
- 不让中间人轻易修改参数；
- 让通用抓包工具只看到二进制。

但“加密”不等于“安全”。样本使用的是分组加密的 ECB 模式（一种最基础的分组模式）：同样的明文块会产生同样的密文块，结构化的参数很容易暴露出重复模式。更合理的做法是使用带完整性校验的 AEAD 模式（可以理解为“加密 + 验伪”一次完成，例如 AES-GCM 或 ChaCha20-Poly1305），并配合随机 nonce（一次性随机数）；如果条件允许，直接使用成熟的 TLS 与标准协议，而不是自研一套加密信封。

还有两个工程细节：

1. **响应类型不能假设**。`data` 可能是 UTF-8 JSON、可能是密文、也可能是空。客户端如果一律按密文解，就会在明文响应上抛 `wrong final block length`。
2. **长度和分块是协议的一部分**。密文拆成几个字段、每个字段多长、空串怎么表示，都会影响服务端解析。只按“算法”复刻，不考虑封装，通常还是跑不通。

## 五、为什么“客户端加密”不是安全边界

这四层叠在一起，看起来很像一道坚固的城墙。但从防守方角度看，真正的结论是相反的：

- 客户端持有密钥，密钥就会泄漏；
- 客户端做签名，私钥就可能被提取；
- 客户端做加密，算法和常量就可能被还原；
- 只要服务端把“本应只在客户端的配置”放到无鉴权接口里，前面三层都会失效。

这不是某一个 App 的问题，而是移动端安全里常见的误区：**把混淆当成加密，把客户端当成可信环境**。

如果我是防守方，会优先做这些事：

1. **不把长期密钥放进客户端**。用短期 token、设备证明、mTLS（双向证书认证）或标准 OAuth，把“客户端能做什么”交给服务端策略。
2. **服务端真正验签**。校验时间戳、随机串、nonce 和重放缓存，而不是只检查字段存在。
3. **密钥可轮换**。任何出现在客户端的密钥都要按“已泄漏”设计，支持快速轮换和吊销。
4. **配置接口最小化**。不要把私钥、白名单、加密开关放在无鉴权接口里；如果已经放了，先轮换，再审计。
5. **错误信息分级**。对外只给通用错误，详细原因写进服务端日志；否则错误码会变成攻击者的“提示器”。
6. **限流与异常检测**。设备指纹、签名和加密都需要配合行为风控，单点防御没有意义。

如果我是研究方，边界同样明确：记录问题、验证影响、负责任地披露；不公开密钥、接口和可复现步骤，不把研究变成“如何使用”的教程。

## 六、协议研究的方法：把“猜”变成“控制变量”

把四层拆开之后，研究过程就不再是“试参数”，而是一组可复现的实验。

### 1. 先观察，不急着解释

记录原始请求和响应：状态码、响应头、原始字节数、耗时、线路、设备字段、时间戳和随机串。不要只记录“成功/失败”，否则后面无法区分是网络问题、代理问题还是协议问题。

### 2. 建立最小模型

先只保留“能让服务端进入下一层”的字段，再逐步补齐。每补一个字段，只改一个变量。错误码在这里不是噪音，而是路标：它通常能告诉你“缺的是哪一层”。

这也暴露了一个防守问题：**错误码越具体，攻击者越容易按图索骥**。对外应该只返回通用错误，把细节留在服务端日志。

### 3. 用测试客户端验证假设

测试客户端的价值不是“能发请求”，而是把假设变成可执行代码：设备指纹、签名、加密、protobuf 封装、响应解析，每一层都能单独替换和回放。这样当协议变化时，能快速定位到哪一层变了。

### 4. 保留可观测性

请求轨迹、原始字节、每层耗时、线路状态、错误分类，这些都应该在测试客户端里可见。协议研究不是一次性的“打通”，而是长期的维护：版本会变、密钥会换、网关会改，只有可观测性才能让下一次排查不用从零开始。

## 七、二进制协议的两个坑

这一层和前端无关，但和“把协议实现出来”强相关。

**第一个坑是整数宽度。** protobuf 的 `int64` 时间戳是 13 位毫秒值，而 protobuf 的整数用 varint（变长整数编码，数值越大占的字节越多）存储；JavaScript 的位运算又是 32 位有符号的。用位移处理 varint，时间戳会被截断，服务端只会回“时间戳过期”。正确做法是用除法逐位处理：

```ts
function varint(value: number): number[] {
  const out: number[] = [];
  let v = Math.floor(value);
  if (v < 0) v = 0;
  while (v > 0x7f) {
    out.push((v & 0x7f) | 0x80);
    v = Math.floor(v / 128);
  }
  out.push(v);
  return out;
}
```

这类问题的可怕之处在于，它看起来像“签名错”，实际是编码层把数字截断了。跨语言复刻协议时，语言差异经常会伪装成协议错误。

**第二个坑是响应类型。** 同一个 `data` 字段，可能在不同接口、不同版本、不同错误路径下返回 JSON、密文或空。客户端不能假设“永远是同一种”，否则会在某个分支上突然失败。稳妥的做法是先看内容特征，再决定是否解密，同时保留原始字节用于回放。

## 八、两条线路的教训：健康检查必须测“真协议”

样本客户端有两条线路：源站直连和 CDN/WAF 边缘（边缘加速节点与 Web 应用防火墙）。它们不是简单的主备关系，因为能力不同：直连能跑加密 protobuf，CDN 可能只能跑明文接口。

这会产生一种很危险的“假可用”状态：

- 页面能打开；
- 列表能加载；
- 点进详情或播放却全失败。

如果健康检查只测明文接口，就会把 CDN 判成“健康”，然后不断把流量切过去。正确的做法是：**健康检查必须测试你真正依赖的协议**，而不是更容易成功的那个接口。

这和快递很像：一家能送文件，一家只能送明信片；不能因为明信片送得快，就把合同交给它。

线路调度也需要明确的失败分类：

- 网络错误、代理返回 HTML、HTTP 424、5xx、协议级“线路不可用”：换线路；
- HTTP 400 / 403：线路是通的，这是业务错误，直接展示；
- 超时：中断并记录，再决定是否换线。

## 九、这件事真正的技术价值

如果只看结果，这是一次“把移动端协议完整复刻”的研究。但从工程角度看，它留下的是四件更通用的东西：

1. **协议分析的本质是建模**。把设备身份、公共参数、签名、加密信封分开建模，比记住某个接口的参数更重要。
2. **客户端不是信任边界**。客户端加密、签名和设备指纹都只能提高门槛；真正的安全来自服务端验签、密钥管理、短期凭证和风控。
3. **协议是类型、顺序和编码的契约**。一个字段写成字符串、一个整数被截断、一个响应类型判断错，都会表现成“接口不通”。
4. **可观测性和回归比“打通一次”更重要**。协议会漂移，线路会变化；能定位、能回放、能回归，才是长期可用的研究结果。

对普通人来说，也可以把这篇文章压缩成一句话：**一个 App 的“网络错误”，背后可能是四道门中的任何一道；而真正的安全，不是把门做得看不见，而是钥匙丢了以后还能守住屋子。**

最后再说一次边界：这是一次针对测试样本的协议研究，不是访问授权，也不是分发工具。文中不提供目标名称、接口地址、密钥或复现步骤；如果研究过程中发现服务端把密钥暴露在无鉴权接口里，正确做法是记录并负责任地披露，而不是把它变成一篇“如何使用”的教程。
