> 这是一次针对测试样本的协议研究与 Web 客户端实现复盘。文中隐去目标名称、包名、接口地址、密钥、设备标识和可复现步骤，不构成对任何服务的访问授权。影视内容版权归原权利人，请勿用于未授权访问或分发。

这个项目最开始的问题很简单：一个只有 Android 客户端的服务，能不能在浏览器里完整跑通请求链，并且把播放体验做到“能日常用”，而不是只证明接口能通。

最后做出来的东西是一个 Vue 3 + TypeScript + Vite 的 Web 客户端：请求层复刻了移动端的加密与签名，内容层只验证协议行为、不内置演示数据，播放器是自己写的 HLS/MP4 控制层，账户、收藏、历史和偏好全部留在本机。它不是一个“下载器”，也不是给谁用的绕过工具；更像一次把不可见的移动端协议拆成可维护前端架构的练习。

## 一、先把“一个请求”拆成四层

移动端协议最容易让人误判的地方，是把它当成“一个加密接口”。真正拆开之后，一个请求至少有四层：

1. **设备身份**：不是随机 UUID，而是由签名证书摘要、包名、版本号等稳定信息派生出的设备指纹。服务端用它做白名单，换一台设备或换一个版本，指纹就不同。
2. **公共参数头**：平台、系统版本、机型、网络、分辨率、应用版本等字段，加上时间戳和随机串，组成一个自定义请求头。
3. **请求签名**：时间戳、随机串和版本号参与签名；签名不是简单的哈希，而是非对称签名，另有一段由对称密钥派生的短校验值。
4. **请求体**：业务参数不是 JSON，而是 `k=v&k=v` 的查询串，拼上时间戳后做块加密，再拆进 protobuf 的多个字符串字段。响应则是一个 `code / msg / data` 的 protobuf 信封，`data` 有时是明文 JSON，有时还要再解一层。

这四层叠在一起，带来的不是“更安全”，而是更高的耦合：设备指纹、签名、加密体、响应解析任何一层对不上，服务端都只会给一个模糊的错误码。调试时最花时间的不是算法，而是确认“现在错的是哪一层”。

一个很典型的教训是：**客户端加密不等于服务端安全**。如果密钥材料最终要落到客户端，它迟早会被提取；如果服务端再把本应只在客户端的配置放到无鉴权接口里，那加密只是增加了正常客户端的复杂度，并没有增加攻击者的成本。这个项目里最值得记录的，不是“密钥怎么还原”，而是“为什么把密钥放在客户端本身就是一个错误的产品决策”。

## 二、浏览器里最麻烦的不是加密，是二进制协议

移动端用 protobuf 很自然，浏览器里就没有那么自然了。这个项目只用到三个 message，所以没有引入 protobuf 运行时，而是写了一个几十行的极简编解码器：只处理 varint、length-delimited 字段和本项目需要的几个编号。

真正踩坑的是 JavaScript 的数值模型。protobuf 的 `int64` 时间戳是 13 位毫秒值，而 JS 的位运算是 32 位有符号的。早期用 `value >> 7` 处理 varint，时间戳会被截断，服务端只会回“请求时间戳过期”。最后改成纯除法：

```ts
function varint(value: number): number[] {
  const out: number[] = [];
  let v = Math.floor(value);
  if (v < 0) v = 0;
  while (v > 0x7f) {
    out.push((v & 0x7f) | 0x80);
    v = Math.floor(v / 128);
  }
  out.push(v);
  return out;
}
```

这段代码本身不复杂，但它说明了一件事：跨端复刻协议时，**语言差异会伪装成协议错误**。如果只看服务端返回码，很容易以为是签名不对；实际是编码层把数字截断了。

另一个坑是响应类型。`ApiResult.data` 在文档里是 `bytes`，实际可能是 UTF-8 JSON、可能是密文、也可能是空。客户端不能假设“永远是密文”，否则会在明文响应上抛 `wrong final block length`。最后的做法是先看内容特征，再决定是否解密；同时保留原始字节数和请求轨迹，出问题时能回放到具体一层。

## 三、两条线路，四种状态

样本客户端有两条线路：一条是源站直连，一条是 CDN/WAF 边缘。它们并不是“主备”关系，因为两条线路支持的能力不同：

| 线路 | 明文接口 | 加密 protobuf 接口 | 结论 |
| --- | --- | --- | --- |
| 直连源站 | 可用 | 可用 | 加密协议必须走这里 |
| CDN 边缘 | 通常可用 | 会被网关改写 | 只能当明文备用 |

这带来一个很反直觉的调度规则：**只有加密协议的探测结果能改变当前线路**。如果只看明文接口，CDN 往往更快、更稳定，但它跑不了加密接口；一旦把当前线路切到 CDN，页面能打开、列表能加载，点进详情或播放却全失败。这就是“假可用”状态。

最终的线路评分是：

```text
score = EWMA 延迟
      + 未知惩罚（还没成功过）
      + 连续失败次数 × 惩罚
      + 协议不可用惩罚（加密接口不可用时直接压到末位）
```

切换还有迟滞：新线路要比当前线路好 15% 且至少快 10ms，才真正切换，避免两条线路在边界上反复抖动。健康检查每 90 秒跑一次，页面隐藏时暂停；统计写入 `localStorage`，10 分钟过期。手动模式则完全跳过评分，方便排查。

请求失败也要分类，不能一律重试：

- 网络错误、代理返回 HTML、HTTP 424、5xx、协议级“线路不可用”错误：换下一条线路。
- HTTP 400 / 403：线路是通的，这是业务错误，直接展示给用户。
- 超时：15 秒中断，记录到线路统计，再决定是否换线。

这套分类看起来琐碎，但它决定了用户看到的是“这个视频不存在”还是“当前线路不可用，已自动切换”。

## 四、CORS 不是配置，是架构约束

浏览器不能直接请求上游，这是整个 Web 客户端最硬的结构约束。解决方案不是“加一个 CORS 头”那么简单，而是在同源路径上做一层可控代理：

```text
/line/<line-id>/api/...  →  对应线路的 /api/...
```

Vite 中间件负责按前缀转发，保留原始请求头和 body，去掉 `host`、`content-length`、`connection` 等 hop-by-hop 头，统一设置 `accept-encoding: identity`，30 秒超时；只允许 `/api` 和 `/chat` 前缀，避免代理变成任意 URL 转发器。代理返回 HTML 时，前端会认为“代理没有生效”，再尝试直连兜底。

生产环境没有 Vite，所以 README 里给的是等价的 nginx 规则。这里的原则是：**代理是客户端的一部分，不是部署细节**。代理的超时、错误码、HTML 检测和路径白名单，都会直接影响前端的失败分类。

播放比 API 更麻烦。HLS 清单里的分片地址是相对的，播放器拿到清单后必须把每一行、以及 `#EXT-X-KEY` 里的 `URI="..."` 重写成同源代理地址；MP4 则要保留 `Range` 请求和 `206` 响应，否则拖动进度条会整段重下。代理里还踩过一个很典型的 Node 坑：上游 HTTP/2 流被 CDN 主动断开时，`Readable.fromWeb` 会异步 `emit('error')`，没有监听器会直接让整个 Vite 进程退出。最后在 `error` 和 `close` 上都做了销毁与收尾。

还有一个媒体地址的坑：有些直链没有 `.mp4` 后缀，只在查询串里带 `mime_type=video_mp4`。如果只按后缀判断类型，播放器会把它当 HLS，直接黑屏。现在的判断顺序是“真实 URL 特征优先，服务端 `format` 字段兜底”。

## 五、播放器：把“能播”做成“能诊断”

播放器是 Hls.js + 原生 `<video>`，但控制层全部自绘：播放/暂停、±10 秒、进度拖拽、缓冲区间、悬停时间、自制音量条、0.75×–2× 倍速、全屏、画中画、自动隐藏控制层、键盘快捷键、断流重试和续播。

真正花时间的是诊断，而不是按钮。播放器右键或按 `I` 会打开一个诊断面板，显示：

- 分辨率、编码、流类型、播放引擎；
- 清单码率、分片实测码率、当前档位；
- 缓冲余量、已缓存分片、已缓存字节、掉帧数；
- 当前进度、总时长、本集预计流量。

码率估算有一个明确的优先级：**分片实测 > 清单 `br` > 分辨率参考值**。本地代理会把 `bandwidthEstimate` 抬高，所以不能直接信 Hls.js 的估算；分片统计更接近真实码率。没有实测值时，才用 720P 2.5 Mbps、1080P 5 Mbps 这样的参考值，并在 UI 里明确标注是估算。

线路级清晰度也不是靠猜。详情页和播放页会用一个隐藏的 `<video>` + Hls.js 探测每条线路的首段，拿到 `videoWidth / videoHeight` 和编码后立即销毁；并发限制为 2，单条 12 秒超时。HEVC 4K 在 Chrome 里无法解码时，会标记“不兼容”并禁用该线路，而不是等用户点进去看一个 `bufferAppendError`。

这套东西的意义在于：播放器不再是一个黑盒。用户看到“720P · 1.24 Mbps”“HEVC 不兼容”“检测失败，可重试”，而不是一个永远转圈的加载图标。

## 六、本机账户：小项目也需要数据边界

这个 Web 客户端没有服务端账号。账户、收藏、历史、播放偏好全部存在浏览器 `localStorage`：

- 密码不存明文，存随机 16 字节盐和 `SHA-256(salt + ":" + password)`；
- 收藏、历史、偏好按 `owner` 分开存，`owner` 是账户 id 或 `guest`；
- 游客第一次注册时，把游客数据迁移到新账户并清空游客副本；后续新账户不重复继承；
- 删除账户时，同时删除该账户的收藏、历史和偏好三组 key；
- 换设备、清站点数据或换浏览器，数据不可恢复。

这不是“安全”的方案，只是一个**数据边界**的方案。`localStorage` 不是保险箱，共用电脑应该退出登录；但即使是本机应用，也应该明确“这份数据属于谁、删除账户时删什么、游客数据怎么迁移”。这些问题不解决，功能越多，数据越乱。

## 七、验证与结果

工程上，最后的验证不是“截图好看”，而是几组可重复的检查：

- `vue-tsc --noEmit`：0 错误；`pnpm build` 成功。
- 路由拆分后，播放页因为 Hls.js 约 641 kB（gzip 约 202 kB），其余页面按需加载。
- CDP 回归覆盖账户隔离（游客迁移、账户甲/乙互不影响、错误密码拒绝删除）、播放诊断（分辨率、分片码率、缓冲、菜单动作）、移动端 390×844 无横向溢出、选集与线路切换保持当前集。
- 所有失败路径都保留服务端错误码和可读原因，不用假数据兜底。

这些验证并不证明“协议永远可用”。目标服务随时可能改协议、改密钥、改网关策略；这个项目能做的，是把变化限制在少数模块里：`crypto / proto / v5 / lines / transport`，而不是散落在每个页面。

## 八、这次项目真正留下的东西

如果只看结果，这是一个“把 Android 协议搬到浏览器”的项目。但从工程角度看，它留下了四件更通用的东西：

1. **协议分析的本质是建模**：把设备身份、签名、加密体、响应信封分开建模，比记住某个接口的参数更重要。
2. **加密不解决信任问题**：客户端持有密钥，密钥就会泄漏；服务端把配置暴露出来，问题只会更大。签名和加密只有配合正确的密钥管理才有意义。
3. **浏览器约束会塑造架构**：CORS、Range 请求、HLS 清单重写、编解码支持，这些不是“前端细节”，而是会反过来决定代理、播放器和错误处理怎么设计。
4. **可观测性不是加分项**：请求轨迹、线路统计、播放诊断、错误分类，决定了出问题时能不能在几分钟内定位，而不是靠猜。

最后还是要说边界：这是一次针对测试样本的协议研究，不是访问授权，也不是分发工具。文中不提供目标名称、接口地址、密钥或复现步骤；如果研究过程中发现服务端把密钥暴露在无鉴权接口里，正确做法是记录并负责任地披露，而不是把它变成一篇“如何使用”的教程。
