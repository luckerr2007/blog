MVSEP 的分离模型覆盖人声、伴奏和常见乐器，质量足以支撑日常工作流，但网页端并不适合反复处理同一批歌曲。官方 API 不返回 CORS 响应头，浏览器无法直连；分离结果的文件链接有时效；模型目录有 128 项，名称和参数都是英文。若音源来自网易云，还要在“搜歌、下载、上传、等待、下载分轨”之间来回切换。

MVSEP Studio 把这些步骤收进本机。它不是分离算法，分离计算仍发生在 MVSEP 的服务器上；本地进程承担的是代理、排队、轮询、缓存和试听。这样浏览器只访问 `127.0.0.1`，API Key、Cookie 和结果文件不需要经过第三方前端。

项目由两个进程组成：

```text
浏览器 ── /api ──▶ Express 8787 ──▶ MVSEP API（按任务固定区域）
                       └──────────▶ Netease_url 5001 ──▶ 网易云
```

## 进程边界

`mvsep-studio/` 是 Vue 3 + Express 应用。开发模式下 Vite 监听 `5173`，把 `/api` 代理到 `8787`；生产模式只开 `8787`，Express 同时提供 API 和构建后的静态文件。服务端显式调用 `app.listen(PORT, '127.0.0.1')`，不依赖框架默认值。

`Netease_url/` 是上游的 Flask 解析服务，负责搜索、取直链和下载。它默认使用 `5000` 端口，而 macOS 的隔空播放接收器（AirTunes）会占用该端口，请求返回 `403`，看起来像服务未启动。项目没有修改上游源码，而是在 `tools/netease/run-netease.py` 中导入 `main` 后覆盖 `config.port`：

```python
import main as app_main
app_main.config.port = PORT
app_main.start_api_server()
```

这样上游仓库保持只读，后续同步版本时只需要处理自己的启动脚本。需要注意的是，Flask 的监听地址由上游决定，启动后应确认实际绑定的是回环地址而不是 `0.0.0.0`。

`start.sh` 负责把两个进程拉起来。它检查 Node 20+ 和可用的 Python，只在缺依赖时安装，只在 `dist` 不存在或源码更新时构建；随后探测端口，能复用就复用，不能复用就清理；启动网易云服务并等待 `/health`，再启动 Studio、打开浏览器，最后在前台监视两个端口。收到 `INT`/`TERM` 时，它先按 PID 文件结束进程，再按端口兜底扫描。

按端口兜底是为了处理孤儿进程。`nohup` 返回的 `$!` 有时是包装脚本的 PID，实际的 `node` 或 `python` 进程挂在它下面；只杀父进程会留下孤儿，下一次启动就会遇到端口占用。

## 任务状态机

MVSEP 的上游状态包含排队、分发、分块处理和合并等多段异步流程。Studio 把它归一为 11 个阶段，每个阶段有固定的进度区间：

| 阶段 | 进度 | 子进度来源 |
| --- | --- | --- |
| `pending` | 0–2 | 固定 |
| `resolving` | 4–14 | 解析请求 |
| `downloading` | 14–34 | 已下载字节 / 总字节 |
| `submitting` | 34–44 | 提交请求 |
| `waiting` | 44–58 | 队列名次 |
| `distributing` | 58–68 | 已完成分块 / 总分块 |
| `processing` | 68–90 | 已完成分块 / 总分块 |
| `merging` | 90–98 | 上游文案中的百分比或分数 |
| `done` / `failed` / `canceled` | 100 | 终态 |

进度只增不减。同一阶段反复查询到相同值时，只更新进度，不追加时间线；只有阶段变化才写一条记录。否则时间线会被轮询写成大量重复项。

任务记录保存在 `server/data/store.json`，最多保留 300 条。写入做了 120ms 防抖，设置、任务和缓存共用一个文件。项目没有数据库，也没有迁移脚本；新增字段依靠 `deepMerge(DEFAULT_STORE, raw)` 补默认值。

服务重启需要对账。崩溃时留下的 `mirroring` 标记会被清除；处于活跃状态但还没有 MVSEP hash 的任务，说明中断发生在本进程，标记为失败；已经有 hash 的任务继续轮询，因为上游可能仍在执行。

## 轮询与限流

轮询器没有引入队列库，只有一个会自我重排的 `setTimeout`：

- 有活跃任务时按 `pollIntervalMs`（默认 5 秒）运行，空闲时降到 30 秒；
- 每轮最多查询 6 条，同时给令牌桶保留 5 次额度，避免一次抽干配额；
- `waiting` 阶段的间隔乘 3，`pending` 乘 4，因为排队名次变化慢；
- 手动刷新与轮询命中同一任务时，用 `inflight` Map 合并成一次请求；
- 新任务提交后调用 `kickPoller(500)` 把下一轮提前，避免界面长时间停在“已进入队列”。

查询失败不会直接判定任务失败。上游抖动很常见，直接判死会让用户重跑并再次消耗额度；失败只累计次数并写入时间线，然后继续重试。`not_found` 单独处理：刚提交的一两分钟内上游经常尚未登记，给 3 分钟宽限期，超过才失败。

MVSEP 的区域必须一致。创建、查询、取消和下载要落在同一个主机上，任务记录保存提交时的 `region`，后续请求都带着它，不跟随当前设置。限流按官方 120 次/分钟留了余量，做成 100 次/分钟的滑动窗口。只有幂等的 GET 会自动重试 3 次；create、cancel、delete 失败直接报错。POST 超时后重发可能已经在云端建了任务，重复扣额度比失败更糟。

上游的错误位置不统一：创建类接口放在 `errors[]`，结果类放在 `data.message`，参数错误在顶层 `message`。客户端把三种都抽出来，`not_found` 作为合法状态返回而不是抛异常，否则轮询会中断。文件字段也有两套：`files` 可能是数组或对象，大小可能是精确的 `bytes` 或字符串 `size`，这些都在客户端归一化。

回源下载只允许 `mvsep.com` 和 `*.mvsep.com`，白名单在试听、下载、ZIP 和镜像四个入口都调用，防止本地服务被当成开放代理。下载先写 `.part`，完成后再改名，进度按字节回调。

密钥管理后来改为池化。提交新任务时在启用的 key 之间轮询，额度用完冷却 10 分钟，密钥无效冷却 30 分钟；查询和取消使用创建任务时的 `tokenId`，避免拿错账户。前端显示各 key 免费额度的总和。

## 网易云解析

`/api/netease/resolve` 有副作用：它让 Netease_url 自己下载文件并返回绝对路径。Studio 利用这一点，把同一路径直接交给 MVSEP，省掉一次复制；只有慢路径才流式落盘到 `downloads/`。

缓存有两层：进程内解析缓存 15 分钟，命中后仍要确认文件存在；`store.json` 的 `cache.neteaseFiles` 是持久索引。两者都不信任“曾经解析过”，文件不存在就重新解析。

端口冲突有专门识别：如果 `5001` 返回 `403` 且响应头包含 `Server: AirTunes`，说明连到的是隔空播放而不是网易云服务。前端会提示修改端口，并自动探测 `5001`/`5000`/`5002`。

音质上限由 `cookie.txt` 决定。模板自带的 Cookie 基本只能拿到 320kbps，无损、Hi-Res 和超清母带取决于账号权限；失败会自动降级，不会让任务卡死。

网易云上游还有几处已知的不一致：`qr_login.py` 的返回类型与当前 `QRLoginManager` 不匹配，交互扫码实际不可用；Docker 的 `entrypoint.sh` 参数没有 argparse 接收；`/search` 解析了 `offset`/`type` 但没有下传。集成时应以实际行为为准，不能照 README 推断。

## 结果、试听与打包

MVSEP 的结果链接会过期，因此分离完成后默认把分轨镜像到 `server/data/results/<jobId>/`。镜像失败只写时间线，不把任务判失败；用户仍可回源试听。

试听接口优先发送本地文件，未镜像时才带 Range 回源。ZIP 用 archiver 流式打包：本地文件直接进包，未镜像的先落 `tmp/`，不会把整张专辑读进内存。

前端没有使用 UI 框架。波形由 Canvas 绘制，播放用 Web Audio 解码，峰值按 URL 缓存在模块级 Map。多轨同步依赖一个全局播放器注册表：`playGroup` 以第一条轨的 `currentTime` 为基准，误差超过 60ms 才纠正，避免多轨之间反复抖动。

模型选择器内置了一份中文知识库：约 60 个常用模型的人工说明、10 张场景卡、30 多条参数解释、70 多条中英文检索词映射。目标不是翻译全部 128 个模型，而是让“只要人声和伴奏”“拆出鼓和贝斯”这类需求能直接落到少量候选上。需要会员的 Ensemble 模型会单独标记，并在提交前拦截。

## 已知限制

- 服务只监听回环地址，没有登录；不要把 `8787` 或 `5001` 暴露到公网。
- Netease_url 本身无鉴权且 CORS 为 `*`，只能接受它运行在本机。
- `store.json` 明文保存 MVSEP token，文件权限和备份需要自行管理。
- `config.mjs` 的默认配置仍有一个硬编码 token 字面量。无论它是否有效，都不应出现在源码中；分享或开源前应删除，并改为首次启动必须自行填写。文档中“单 token”的描述也与当前的密钥池不一致。
- 文档里的旧路径仍是 `~/Documents/项目/MVSEP`，实际位置已经移到 `audio/MVSEP`。
- 它不提供分离算法。MVSEP 不可用时，核心流程不可用；本项目的价值在编排和本地缓存。
